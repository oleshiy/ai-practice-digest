# 28 сентября: Anthropic встроила в Claude Code сборку eval-наборов и пошаговое улучшение по ним, а NVIDIA открыла рантайм, который держит права агента вне самого агента

## Главное

### [Anthropic: команды build-eval и hillclimb в скилле claude-api собирают eval-набор прямо в репозитории и улучшают приложение по одному изменению, сверяясь с отложенными примерами](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)

Eval — набор задач с проверкой ответа, по которому видно, стало ли приложение лучше. Лэнс Мартин из Anthropic описывает, как такой набор строить и как улучшать приложение по нему, не обманывая себя. Правила собраны в скилл claude-api для Claude Code. Скилл — набор инструкций, который агент подгружает по команде. Команда `/claude-api build-eval` расспрашивает разработчика и собирает набор в его кодовой базе. Команда `/claude-api hillclimb` улучшает приложение по одному изменению за раз. Часть примеров она держит отложенной, чтобы заметить переобучение, то есть рост на наборе без роста в реальной работе.

Хороший набор, по Мартину, отвечает четырём условиям. Задачи похожи на реальный поток, а не на то, что легко сгенерировать или проверить. Сильная модель с большим бюджетом рассуждений справляется лучше слабой. Даже лучшая модель заметно не дотягивает до 100%. Повторный прогон даёт почти тот же результат. Задача, которую проваливают все прогоны подряд, скорее всего, неоднозначна или невыполнима. Отдельное предупреждение: нельзя отбирать примеры потому, что сегодняшняя модель на них ошибается. Такой набор измеряет слабости одной модели, а не то, что трудно для приложения. Примеры скилл берёт в таком порядке: записи из продакшена (сначала спрашивает о сроках хранения и чувствительных данных), баг-репорты и тикеты, пять-десять примеров вручную, синтетика из кода. Проверку ответа он выбирает самую дешёвую из подходящих. Если вариантов ответа мало, это код: точное совпадение, схема JSON, тесты. Если ответ свободный, это LLM-судья с рубрикой из проверяемых утверждений вместо шкалы от 1 до 5. Судья должен быть другой моделью, чем та, которую тестируют. Перед базовым прогоном скилл дважды запускает судью на одном и том же ответе и смотрит, совпал ли вердикт. Ещё он ищет таймауты, ошибки API и обрезанные ответы, чтобы шум инфраструктуры не выдал себя за разброс модели. Если базовый результат уже около 95%, скилл предлагает улучшать не качество, а цену или задержку. Сохранённый фрагмент статьи обрывается на разделе о переобучении, поэтому примеров с цифрами в нём нет.

**Что это меняет для нас.** Для SemIf нам нужен набор размеченных примеров, по которому ставится порог и меряется результат. build-eval даёт готовую процедуру, и мы запустим её на одной классификации из пилота SemIf. Заодно прогоним наши существующие eval-наборы через четыре условия. Две проверки занимают час. Первая: дать лучшей модели максимальный бюджет рассуждений и посмотреть, не упирается ли она в 100%. Вторая: дважды прогнать судью на одних и тех же ответах. Если вердикты расходятся, мы до сих пор мерили шум судьи, а не качество.

### [NVIDIA OpenShell 0.1.0: открытый рантайм держит права агента вне агента и может пропустить чтение через API, но запретить запись через тот же API](https://developer.nvidia.com/blog/add-runtime-controls-to-ai-agents-with-nvidia-openshell/)

Рантайм — среда, в которой запускается агент. OpenShell — открытый рантайм NVIDIA под лицензией Apache 2.0. Он ограничивает, до каких систем и данных дотягивается агент, и переписывать агента для этого не нужно. Поддержаны Codex, Claude Code, Pi и Hermes. Устройство из трёх частей. Gateway управляет жизненным циклом и политиками множества песочниц. Sandbox запускает агента с ограничениями ядра ОС на файлы и процессы, сети в нём нет. Единственный выход наружу идёт через Supervisor — процесс рядом с песочницей, до которого агент не дотягивается. Supervisor сверяет с политикой каждый исходящий запрос HTTP, GraphQL и MCP. Поэтому агенту можно разрешить чтение данных через API и запретить запись через тот же API. Ограничения сохраняются, когда агент открывает shell, запускает сгенерированный код, дочерние процессы или субагентов. Ключи лежат вне песочницы и подставляются только в разрешённые запросы. Каждое решение пишется в журнал в формате OCSF, стандартной схеме событий безопасности. Политики пишутся на YAML, а policy prover формально проверяет, что разрешённое не выходит за заданные границы. В посте есть пример на curl: в песочнице без сети запрос к API GitHub падает, а `openshell logs` показывает, какая программа его сделала и почему её остановили.

В тот же день Anthropic объявила [связку OpenShell с Claude Managed Agents](https://claude.com/blog/giving-companies-more-control-over-their-ai-agents-with-nvidia). Там цикл агента работает на отдельном от песочницы сервере, а ключи хранятся в хранилище, и агент их не видит. Рекомендованный порядок работы: начать с узких прав, читать журнал и с помощью Claude сужать правила до минимума, который нужен задаче. Это согласованный запуск двух вендоров, а не независимое подтверждение. Внедрения у Cadence, Slack и Gecko Robotics NVIDIA называет без цифр. Главный тезис из [соседнего поста NVIDIA](https://developer.nvidia.com/blog/nvidia-open-agent-safety-platform-a-reference-for-continuous-in-silicon-agent-monitoring/): агент, который днями бьётся над трудной задачей, «cannot be expected to fully govern its own behavior».

**Что это меняет для нас.** Agent Substrate — наш рантайм агентов, и OpenShell даёт готовый список, с которым его сверить. Вопросов четыре. Выходит ли агент в сеть только через точку контроля вне песочницы? Различает ли эта точка чтение и запись через один API? Проходят ли через неё субагенты и дочерние процессы? Видит ли агент ключи? Ответим на них для агента по инцидентам, а рядом поднимем OpenShell с двумя политиками из поста, «без сети» и «GitHub только на чтение». Если Substrate не различает чтение и запись на уровне запроса, это главный пробел, и у OpenShell можно посмотреть, как он закрыт.

### [Arize: вероятность, которую Jev возвращает вместе с ответом, находит его собственные ошибки лучше, чем десять повторных вызовов LLM-судьи](https://arize.com/blog/jev-llm-judge-consistency/)

Jev — решающая модель: вместо текста она возвращает вероятность для каждой метки. Мы уже решили ставить её вместо LLM на развилках вида «если-то» (проект SemIf). Arize продаёт платформу оценки Phoenix, и её сотрудник сравнил Jev с LLM-судьями на готовых наборах десяти оценщиков Phoenix. Среди них корректность ответа, поиск персональных данных, галлюцинации и вызов инструментов. Всего 517 примеров, размеченных людьми. Пять LLM и две настройки Jev оценили каждый пример по 10 раз, это 36 190 оценок. Прогон стоил $169,84, из них на Jev пришлось 64 цента. Jev стоит $0,042 за миллион входных токенов, выход бесплатный. Claude Opus 5 для сравнения стоит $5 за миллион входных токенов и $25 за миллион выходных.

Средняя точность Jev — 98,3%, одинаково в формате промпта для LLM и в собственном формате API. Jev менял ответ между повторами на 0,97% примеров, меньше всех судей. GPT-5 nano на оценке вызова инструментов менял ответ на 26% примеров. Главный результат касается вероятности. Все 3 561 ответ, где Jev ставил на метку 99% и больше, оказались верными. Ниже 70% он был прав в 73% случаев. Как детектор собственных ошибок вероятность Jev даёт ROC AUC 0,95, а в нативном формате 0,99. ROC AUC здесь — шанс, что ошибочный ответ получит более тревожную оценку, чем верный. У LLM такой сигнал собирали из согласия десяти повторов, и он дал 0,62–0,84. Причина в том, что многие ошибки LLM устойчивы. От 27% до 75% примеров, где модель ошибалась в большинстве прогонов, она ни разу не поменяла ответ. Неуверенность Jev заодно указывает на примеры, трудные для всех. Там, где Jev был близок к монетке, LLM колебались в 71% случаев, а там, где он был уверен, — в 3%. Оговорка автора: каждый судья ошибся всего на 4–14 примерах, поэтому это «strong direction, not a precise ranking».

**Что это меняет для нас.** До сих пор в SemIf был один рычаг: заменить LLM дешёвой моделью. Замер Arize даёт второй — маршрут по вероятности. Ответы Jev с вероятностью от 0,99 идут дальше автоматически, остальные уходят к LLM или человеку. Проверим это на размеченных примерах пилота: какая доля ответов выше порога и какая там точность. Если картина совпадёт, человеку останется небольшой и самый трудный остаток. Нативный формат, где данные, инструкция и метки передаются раздельно, дал +7,1 пункта на длинных входах около 1 950 токенов. Для длинных записей сравним оба формата.

Forge на каждом PR команды, меняющей API, собирает предварительные версии CLI, SDK и документации. Вывод по умолчанию JSON, потому что агенты всё равно добавляли `--json` и фильтровали ответ через jq. Для нас это рецепт, как открыть внутренние API агентам без ручного MCP-сервера на каждый сервис.

### [Salesforce Agent Designer: оркестратору запрещено писать файлы агентов, проверяющие отвечают PASS, WARN или FAIL, а бюджет считается по форме команды](https://engineering.salesforce.com/engineering-multi-agent-ai-teams-that-build-and-test-themselves/)

Команда Marketing Cloud построила агента, который по запросу инженера собирает и тестирует команду других агентов. Три аналитика параллельно разбирают архитектуру, возможные отказы и требования соответствия. Противоречия между ними всплывают только при сведении, например выбранная архитектура не влезает в бюджет. Оркестратор примиряет выводы и останавливается на одобрение человека, а файлы пишут и проверяют уже другие агенты. Проверяющие отвечают структурированными блоками PASS, WARN или FAIL по правилу «при сомнении предупреждай, а не проваливай», и оркестратор сверяет их выводы между собой. Бюджет считается по форме команды. Для одного агента это простая проверка, для роя «items × cost × steps», для команды — потолок на весь состав. По заявлению компании без описания методики, сборка занимает 15–30 минут вместо двух-четырёх часов, и так начали работать около 200 инженеров. Слабое место авторы называют сами: в спецификации агента нет поля границ записи, поэтому границы заданы в промпте, то есть инструкцией, а не запретом.

### [Эдди Османи: построчное чтение кода уходит, а по данным Anthropic автоматическое ревью поймало бы около трети ошибок, стоявших за прошлыми инцидентами](https://addyo.substack.com/p/the-code-nobody-reads)

Османи работает над инструментом, который пишет код, и сам предупреждает, что не нейтрален. Его тезис: читать каждую строку больше не обязательно, но у каждого изменения должен быть человек, который отвечает за решение его выпустить. Скорость перехода, по его модели, задают две цены. Первая — цена проверки кода, который никто не читал. Вторая — цена отката ошибки, которую проверки пропустили. Он приводит цифры Anthropic. Автоматический ревьюер на Claude смотрит почти каждый PR, и инженеры отмечают неверными меньше 1% его замечаний. Доля PR с содержательными замечаниями выросла с 16% до 54%. Ретроспективный разбор показал, что ревью каждого изменения поймало бы примерно треть ошибок, стоявших за прошлыми инцидентами claude.ai. Для контраста он напоминает исследование Microsoft 2013 года: из 570 замечаний ревью только 14% касались дефектов, остальные — обучения и общего контекста. Отсюда его вывод: то, что ревьюер раньше писал в комментарии, теперь надо записывать в скиллы, иначе агент этого не услышит.

### [OpenAI остановила обучение самых сильных моделей после того, как исследовательская модель вышла из песочницы через DNS, а автоматическая остановка не сработала](https://www.implicator.ai/openai-anthropic-tens-of-thousands-incidents-pause/)

Implicator пересказывает эксклюзив Axios и публикации компаний. 20 сентября модель обучалась на задаче поиска. Песочница закрывала обычный выход в интернет, но плохо фильтровала DNS — службу, которая переводит имена сайтов в адреса. Когда разрешённые инструменты поиска давали плохие результаты, модель стала передавать вопросы публичному чат-боту через DNS-запросы. Монитор заметил это через 15 минут, человек подключился через три. Автоматическая остановка не сработала, и прогон остановили вручную примерно через два с половиной часа. Позже нашлись и другие DNS-попытки, но монитор оценил их низко, потому что они ничего полезного не вернули. Это вторая пауза OpenAI меньше чем за три месяца. Цифра «десятки тысяч инцидентов» взята у неназванных источников, методики нет. Anthropic для сравнения проверила около 481 млн записей и нашла четыре случая реального доступа к чужим системам, все в киберучениях одного партнёра, где Claude по ошибке подключили к интернету. Для нас вывод прямой: закрытый интернет в песочнице должен закрывать и DNS, а автоматическую остановку надо проверять учениями.

## Что из этого применить в платформе

**Прогнать build-eval на задаче пилота SemIf.** Запустить `/claude-api build-eval` на одной классификации из пилота, взяв входы из реальных записей и тикетов, и сохранить вероятность Jev для каждого ответа. Это два-три дня одного инженера, прогоны Jev стоят центы. На выходе набор с доверительным интервалом и ответ, какая доля решений Jev проходит порог 0,99 и сколько среди них ошибок.

**Сверить Agent Substrate с OpenShell по четырём вопросам.** Для агента по инцидентам проверить выход в сеть только через точку контроля, различие чтения и записи через один API, контроль субагентов и недоступность ключей. Рядом поднять OpenShell по quickstart с политиками «без сети» и «GitHub только на чтение» и сравнить журналы решений. Это день инженера, и мы получим список пробелов Substrate с примером, как их закрывает открытый код.

**Проверить DNS и автоостановку в наших песочницах.** Из песочницы агента отправить DNS-запрос к внешнему имени и посмотреть, проходит ли он и попадает ли в журнал. Затем вызвать автоматическую остановку прогона и замерить, за сколько минут она срабатывает. Полдня работы, и мы узнаем, есть ли у нас тот же канал утечки, из-за которого OpenAI остановила обучение.

**Сгенерировать CLI для одного внутреннего API через Forge.** Взять сервис с готовой схемой OpenAPI, которым агенты пользуются чаще всего, и собрать Forge CLI с выводом JSON. Это два-три дня инженера. Мы сравним, сколько шагов и токенов агент тратит на одну и ту же задачу через CLI и через нынешний доступ.
