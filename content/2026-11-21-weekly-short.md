### OpenAI представила GPT‑6.2 Astra и Sol 17 ноября

Astra предназначена для сложных проектов, Sol — для повседневной работы, в том числе разработки. По сравнению с GPT‑6 Astra вход и выход новой Astra подешевели на 20%. Sol сохранила цены GPT‑6.1 Sol. [Анонс GPT‑6.2](https://openai.com/index/introducing-gpt-6-2-astra-sol/)

В режиме Standard при входе до 272 000 токенов включительно цены за миллион токенов такие.

**Astra** — $8 за вход, $0,40 за чтение из кэша, $40 за выход.

**Sol** — $2 за вход, $0,10 за чтение из кэша, $10 за выход. [Тарифы OpenAI](https://developers.openai.com/api/docs/pricing)

#### Скидка на фоновые запросы

Если первый ответ может подождать, в Responses API для Astra и Sol можно выбрать целевое окно в два или восемь часов. Тогда токены фонового запроса стоят на 30% или 40% дешевле Standard соответственно. Например, при коротком входе миллион выходных токенов Astra в восьмичасовом режиме стоит $24 вместо $40. ### LangSmith показывает, сколько агент потратил на конкретный pull request и почему

Одна правка может пройти через несколько сессий агента. LangSmith связывает эти сессии с pull request: команда видит, сколько стоили вызовы моделей и вошла ли правка в основную ветку.

Самое полезное — из дорогого PR можно перейти в историю работы и понять, откуда взялась сумма. Например, для мелкой правки агент использовал дорогую модель. Или в одной сессии решали несколько задач подряд, и с каждым новым запросом приходилось заново оплачивать всё более длинную историю. В первом случае стоит пересмотреть выбор модели, во втором — начинать новую сессию при смене задачи.

[Как LangSmith связывает расходы кодовых агентов с pull request](https://www.langchain.com/blog/langsmith-coding-agents-roi)

### Microsoft выпустила TokenEconomizer: кодовый агент запоминает, как работать с репозиторием, и тратит меньше на следующих задачах

Кодовый агент может раз за разом тратить токены, чтобы выяснить, как в проекте запускать тесты. TokenEconomizer сохраняет удачные команды и подсказывает их в следующих сессиях. Например, в репозитории SymPy агент Claude Code сначала пытался запустить отсутствующий `pytest`. С подсказкой он сразу использовал штатную команду проекта и выполнил задачу за 11 ходов вместо 15.

Microsoft Research проверила плагин на 277 задачах в шести репозиториях. С Claude Code и Sonnet 5 средняя стоимость токенов на задачу снизилась на **23,6%**, а доля задач, решённых с первой попытки, выросла с **74,7% до 76,0%**.

[Исследование Microsoft Research](https://www.microsoft.com/en-us/research/blog/tokeneconomizer-learning-from-experience-to-make-ai-coding-agents-more-efficient/) · [Плагин на GitHub](https://github.com/microsoft/TokenEconomizer)

## Инженерные практики

### Какими тестами проверять код агента: команда Claude Code ставит E2E на первое место

#### Какие тесты дают больше пользы

1. **E2E — первый выбор.** Агент проходит реальный пользовательский сценарий. При сбое видны последний успешный шаг, состояние приложения и снимок экрана.
2. **Тесты свойств находят пропущенные крайние случаи.** Разработчик задаёт инвариант, например «повторная миграция ничего не меняет». Библиотека проверяет его на тысячах сгенерированных входов.
3. **Дифференциальные тесты полезны при миграциях.** Старой и новой системам подают одинаковые входы, сравнивают результаты и отдельно фиксируют допустимые отличия.
4. **Исполняемый тест достаточно написать один раз.** Дальше его можно часто запускать как обычную программу с минимальными дополнительными затратами токенов.

#### Как проверяют изменения в Claude Code

5. **Агент запускает изменённое приложение до коммита.** Проектный навык `/verify` описывает запуск и проверку через браузер, симулятор или API. Карта функций подсказывает пользовательские маршруты и ожидаемый результат.
6. **Быстрые проверки идут первыми.** Тесты, сборка и линтер выполняются локально до открытия PR. Медленная обратная связь заставляет агента накапливать изменения, и причину сбоя сложнее найти.
7. **После трёх неудачных раундов исправления подключают человека.** Проверки пишет владелец кода. Сработавшая проверка должна объяснять, зачем нужен его разбор.
8. **Прошлые инциденты проверяют выборочно.** Из 39 проверок агент по содержанию diff обычно выбирает 3–10. Например, изменение формата сообщений запускает проверку загрузки старых диалогов.
9. **Один настроенный ревьюер часто полезнее второго, более дорогого.** Каждый новый проход получает выводы предыдущего и историю пропусков.
10. **Правка не может ослабить собственное ревью.** Правила берут из базовой ветки. Одобрение относится к конкретному коммиту и теряет силу при изменении кода.
11. **Новую блокировку сначала наблюдают в действии.** Режим `observe` показывает, какие коммиты были бы остановлены. Для каждого коммита сохраняют способ проверки, включая её отсутствие.

#### Как проверяют самих проверяющих

12. **Ревью испытывают на реальных пропущенных дефектах.** Восстанавливают репозиторий на момент ошибки и засчитывают обнаружение именно этой ошибки. Исправные изменения похожего размера служат контролем ложных тревог.
13. **Пропуски измеряют на каждом этапе.** Отдельно смотрят, что агент заметил, что прошло перепроверку и что дошло до итогового ревью. Так видно, где система потеряла уже найденную ошибку.
14. **Важность замечания оценивают отдельно от его правильности.** Различают существенный дефект, мелочь и проблему, которая существовала до этой правки. Наборы для настройки и итоговой оценки разделяют.
15. **Новое правило должно выдержать проверку.** Для повторяющегося замечания ищут минимум два PR и распознаваемый признак в diff. Три агента пытаются найти контрпример, затем правило утверждает человек. Известные инциденты дополнительно переигрывают, чтобы установить, мог ли ревьюер вообще заметить дефект.
16. **Нестабильный тест учит агента перезапускать его до успеха.** Команда запрещает скрывать сбой повторами и задержками. Если причину установить не удалось, тест удаляют с письменным объяснением. Накопленные тесты и правила регулярно пересматривают.

[Оригинальная статья команды Claude Code](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)

### Spotify — когда изменение можно выпускать по офлайн-оценке, а когда нужен A/B-тест

Spotify предлагает проверить саму офлайн-метрику на истории запусков. Для каждого прошлого изменения нужны два числа: насколько изменился балл на тестовом наборе и насколько изменилась выбранная продуктовая метрика в A/B-тесте. Так можно ответить на вопрос: **когда новая версия выигрывала у старой на столько баллов, как часто пользователям в итоге становилось хуже?** Совпадение оценок модели-судьи с мнением экспертов само по себе на этот вопрос не отвечает. [Статья Spotify Engineering](https://engineering.atspotify.com/2026/11/when-can-you-ship-on-offline-evals-alone)

**Отсюда три решения.** Если офлайн-выигрыш достаточно велик для выбранного командой уровня риска — выпускать. Если проигрыш достаточно велик — отклонять. Всё, что между этими порогами, — отправлять в A/B. Универсального порога вроде «+3 балла достаточно» нет. Чем слабее офлайн-результат предсказывает поведение пользователей, тем шире зона A/B. [Методика расчёта](https://arxiv.org/abs/2610.10142)

**Показательный пример — 183 эксперимента с заголовками Upworthy.** Модель оценивала, насколько ясно заголовок раскрывает содержание статьи. В реальном эксперименте измеряли клики. Изменение ясности объясняло лишь около **2,3%** разброса изменений кликабельности даже после поправки на шум. При заданном в исследовании пороге риска **все 183 случая отправились в A/B**. Можно достаточно точно измерять ясность заголовка и всё равно почти ничего не знать о том, как изменятся клики. [Данные и расчёт](https://arxiv.org/html/2610.10142v1#S7.SS2)

**Ещё четыре находки из статьи:**

- **Поправки к промпту и замены модели стоит проверять раздельно.** Если смешать разные классы изменений, в общей выборке может появиться сильная связь, которой нет ни в одной группе по отдельности.
- **Шум способен скрыть полезную метрику.** В модельном примере истинная связь объясняла 60% вариации онлайн-эффекта, а прямой расчёт по шумным измерениям показал лишь 24%. Это симуляция, а не результат запуска Spotify.
- **У модели-судьи особенно опасно предпочтение одного варианта.** Если она завышает оценку ответам конкретной модели, при сравнении моделей может поменяться даже знак результата: ухудшение будет выглядеть как улучшение.
- **Часть уверенных решений тоже должна попадать в A/B.** Если проверять на пользователях только спорные случаи, команда перестанет замечать ошибки именно там, где уже доверила выпуск или отказ офлайн-оценке. Автор предлагает случайно отбирать для A/B часть обоих крайних случаев. В самой Spotify офлайн-проверки используют для быстрой итерации и продолжают сочетать их с онлайн-экспериментами. [Разбор ограничений и практики Spotify](https://engineering.atspotify.com/2026/11/when-can-you-ship-on-offline-evals-alone)

### LangSmith Tool Gateway — один набор инструментов для разных агентов с разными правами

В статье есть показательный пример ритейлера: **больше 50 MCP-серверов и свыше 1 000 инструментов**. Помощник в магазине отвечает на вопросы об остатках с правами конкретного сотрудника. Ночной агент в 3:00 сверяет запасы со своей служебной учётной записью. Оба обращаются к одной системе, но шлюз при каждом вызове определяет, чьи полномочия использовать. При включённой трассировке видно, кто вызвал какой инструмент, от чьего имени и с каким результатом. [Пример ритейлера](https://www.langchain.com/blog/langsmith-tool-gateway)

**Один набор инструментов LangSmith Tool Gateway можно переиспользовать в Claude Code, Cursor и собственном агенте.** Платформенная команда один раз подключает MCP-серверы, выбирает нужные операции и получает один MCP URL. Для своего агента достаточно поддержки MCP по Streamable HTTP и возможности передать ключ LangSmith в заголовке. Разработчикам обоих агентов не приходится по отдельности реализовывать OAuth и хранить токены системы учёта. [Подключение клиентов](https://docs.langchain.com/langsmith/tool-gateway-clients)

Набор инструментов определяет, что агент *видит*. Отдельная политика при самом вызове определяет, что ему *разрешено выполнить*. Например, агенту можно показать инструмент записи в хранилище, но сам запрос шлюз передаст только после подтверждения человеком, если для этой операции задано такое правило. [Как обрабатывается вызов](https://docs.langchain.com/langsmith/tool-gateway)

Если добавить к URL `?mode=search`, клиент увидит всего три операции — `search_tools`, `get_tool` и `call_tool`. Агент найдёт нужный инструмент и загрузит его описание по запросу. Правила доступа продолжат действовать для конкретного инструмента при вызове. [Режим поиска](https://docs.langchain.com/langsmith/tool-gateway-clients#use-search-mode-for-large-kits)

Для самого Tool Gateway документирована облачная бета на тарифах LangSmith Plus и Enterprise. Внутренние MCP-серверы могут оставаться в сети компании и подключаться через исходящий туннель. Учётные данные подключённых сервисов при этом хранятся в LangSmith. [Условия размещения](https://docs.langchain.com/langsmith/tool-gateway) · [Подключение внутренних сервисов](https://docs.langchain.com/langsmith/tunnels)

### Как Hermes превращает удачные решения сотрудников в скиллы для команды

В Microsoft Teams сотрудник может поручить Hermes подготовку документа или разбор входящей почты. Когда задача повторяется, Hermes сам сохраняет удачный способ её выполнения как личный навык. Агент описывает порядок действий текстом, а стабильные шаги оформляет в код, который можно запускать повторно.

Через функцию Collective Wisdom сотрудник спрашивает у Hermes, какими из его навыков стоит поделиться, и предлагает выбранный навык на проверку. После проверки его публикуют для команды. Коллеги могут использовать готовый навык, когда им поручают такую же задачу. [Как устроены навыки в Hermes Enterprise](https://nousresearch.com/hermes-enterprise-in-microsoft-teams)
